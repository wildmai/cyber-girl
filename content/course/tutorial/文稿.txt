把今天有点累，陪我聊聊，输入这个窗口。屏幕上看起来只是一次聊天，背后却需要麦克风、识别模型、对话模型、语音合成，以及人物视频共同完成。这节教程不从模型排行榜讲起，而是沿着这句话，把 cyber girl 从最初需求到部署和发布的开发过程走一遍。你会看到真实产品界面和当前代码摘录。流程动画用于解释机制，不是实时性能演示。我们会明确区分已经验证的功能，以及仍需要目标 Mac 实测的部分。
最初目标是纯本地、无密钥的 AI 陪伴应用，希望四个模型控制在十五 GiB 显存内。实际开发先接通在线文本后端，再加入声音和数字人，最后恢复本地大脑。这里要先区分两个运行路线。本地路线使用 Silero、Whisper、Qwen 和 MuseTalk，第一次准备权重需要联网。另一条路线保留自己的识别后端，接入在线对话和第三方数字人。最终保留 MuseTalk，不再扩展其他人物框架。十五 GiB 是最初预算目标，不是已经完成的显卡峰值实测。
先看目录。app main 管理 HTTP 和 WebSocket，pipeline 连接四个工作阶段，models 管理权重，sessions 管理每个人的状态。网页的 app 点 js 负责录音、交互和播放，audio worklet 处理声音帧，captions 控制字幕。人物模块分别管理本地口型与第三方数字人连接。scripts 提供模型准备和启动，deploy 负责服务器，desktop 负责桌面外壳。上游 speech to speech 的线程管理和 VAD 迭代器放在 vendor，许可与修改说明也一并保留。清楚职责之后，调试才不会每次都从整个项目重新猜。
如果你使用 M 系列 Mac，先安装 Homebrew，用 GitHub 命令行登录有权限的账号，然后克隆 cyber girl。当前仓库保持私有，需要授权访问。进入项目，执行 setup mac 点 command，安装 Python 三点一一、FFmpeg、SoX 和依赖，再准备五组模型。安装完成后，运行 start mac 点 command。它启动原生服务，并打开本机七八六零端口。以后可以直接双击这个启动文件。这里的命令是操作示范，不是已经在目标 Mac 执行成功的录屏。完整命令也在文字教程中，适合复制或逐步检查。
第一次从 GitHub 拉取，与拿到已经准备好的开发目录不是一回事。Git 仓库不包含模型权重，所以不能依赖开发机器的缓存。我们在准备脚本里固定 Silero 和 Whisper 的下载来源、大小和 SHA 二五六。对话模型同样固定 revision，只下载 Q 四 K M 那一个 GGUF，不下载完整的高精度仓库。Qwen 三 TTS 必须保留完整快照及语音 tokenizer。MuseTalk 也需要多组配套权重。下载是显式安装步骤，正常运行只读本地文件。这解决了开发机能运行，干净克隆却缺模型的问题。
点击开始对话后，先确认浏览器真的拿到了麦克风声音。用户授权设备，不代表音频上下文一定恢复运行；声卡默认设备也可能是没有输入的虚拟通道。因此页面要提供输入设备选择、声音电平和错误提示。调试时，先看百分比有没有变化，再看后端有没有收到 PCM 首帧。如果电平一直为零，先检查设备和系统静音。本次服务器语音故障，最后就是通过切换到实际麦克风恢复的。不要在没有声音输入时，反复修改大模型提示词或者重建数字人会话。
声卡可能以四万四千一百或四万八千赫兹采集，Silero 接收的却是每秒一万六千个样本。前端 AudioWorklet 先重采样，再将浮点音频变成小端 PCM 十六。每五百一十二个样本组成一帧，每个样本两个字节，所以一帧是一千零二十四字节，大约三十二毫秒。后端检查这个长度，再把二进制帧放进 VAD 队列。采样率、声道数和字节顺序必须一致。否则即使网络连接正常，模型听到的也可能是变速或失真的数据。
VAD 不理解你说了什么，它只判断哪里有人声。Silero 的迭代器保存跨帧状态，在说话前后补上一小段声音，再等停顿超过配置阈值，把这一句送给识别模型。当前最短静音配置是六百五十毫秒，补边一百六十毫秒。连续长讲话也有长度上限，避免麦克风一直打开时缓冲无限增长。多人应用必须为每个人保留独立的 VAD 状态。还有一个容易漏掉的细节：用户持续说话时，活动时间要持续刷新，不能只在开始说话那一刻更新。
一句话切好以后，Whisper 才开始识别。应用使用本地 PT 权重路径，指定中文，并将识别结果作为用户消息发送到界面。这样你能区分识别已经结束，还是模型还没有收到输入。大权重可以共享，但共享的 Whisper 推理通过锁依次执行，避免状态和内存峰值混乱。这也意味着，CPU 服务器上多个人同时讲话，可能需要排队。独立会话解决私人状态隔离，不会凭空增加计算能力。排查延迟时，要分别记录 VAD 停顿、识别耗时、生成耗时和播放等待。
现在把四个阶段连起来。每个工作项除了内容，还有一个生成代次。用户开始新一轮或点击停止时，当前代次递增，旧队列清空，文本流被取消。无法瞬间停止的本地推理可以继续完成，但它的结果已经属于旧代次，不会再次播放。浏览器也必须清空自己的音频和视频队列，并立即静音。只停止后端线程，已经到达扬声器的声音仍会继续；只暂停播放器，旧任务又可能把视频塞回来。生成代次把计算、事件和播放统一在同一个取消边界上。
对话管线不应该绑定某个供应商。它需要的是能流式返回可见文字，并且可以取消和关闭的接口。在线后端与本地后端都遵循这一约定。本地使用应用管理的 llama server，只监听回环地址，用 GGUF 文件启动。上下文限制为四千零九十六个 token，关闭思考输出，再访问兼容的聊天流式接口。对话输入始终带上当前人设和最近上下文。读取结果时只转发可见内容，额外过滤跨 token 分裂的思考标签。这一步的自动化验证证明适配和生命周期正确，并不等于目标 Mac 的完整九 B 性能已经验证。
如果页面写着小满，而模型并不知道这个名字，人设就只是装饰。正确做法是在每一轮生成请求前，读取当前 PersonaStore，并构造 system 消息。默认设定是成年女性的 AI 女友，温柔、甜美，认真倾听，也有自己的幽默感。用户可以修改名字、身份、性格和表达方式。保存时清空当前模型上下文，保留浏览器聊天存档，让新一轮真正采用新的设定。存档和上下文也要分开管理，不能刷新页面就把整份历史自动重新发送。
模型吐出一句文字之后，Qwen 三 TTS 才开始合成声音。这里最常见的误判是，接口已经返回文字，就认为语音也应该立刻播放。实际上还要经过合成、编码、传输、解锁浏览器声音，以及媒体真正开始播放。CPU 上短句也可能等待数十秒，所以界面必须区分正在思考、正在合成和正在播放。我们最终以用户实际听到声音为闭环验收，而不是只检查 WAV 文件存在。人物生成失败时也保留声音回复，让系统先完成最核心的陪伴功能。
左侧文字过早全部出现，会破坏对话节奏。修复方式不是给字幕随便加一个固定延时，而是从真实媒体播放事件开始，用媒体时钟驱动进度。本地 WAV 和 MP 四都有自己的播放时间。字符按中文、英文、标点和空白分配不同权重，再逐步揭示。第三方实时音视频没有逐字时间戳时，使用可听音量采样累计进度，并把最后几个字留到这一轮结束。它是播放同步的估算方式，不是严格的逐字对齐。停止和切换代次时，字幕计时器也必须一起清理。
静态照片不会因为播放声音就自动获得嘴形。MuseTalk 接收人物照片和已经生成的语音，为这一句生成口型视频。页面播放带声音的 MP 四，不再重复播放原始 WAV。它解决的是口型同步，不是全身动作和情绪表演。历史 CPU 实测里，零点六秒口型片段约需要二百一十八秒计算，另一段一点五二秒视频约需要二百九十三秒。这些数字用于说明性能边界，不应转成低延迟实时的宣传。本机能生成，和速度适合互动，是两个独立的验收目标。
另一条路线接入第三方数字人，接收云端生成的声音和人物画面。为了让微笑、点头和说话内容保持一致，实时模式让对话模型同时规划台词和动作，再用结构校验检查完整结果。比如用户累了，先表达理解，再给出自然的小幅微笑和放松动作，而不是无论说什么都重复同一套表情。浏览器作为观众订阅音视频，长期密钥留在服务端。这里需要区分人设约束、动作提示和生成结果：提示能影响表现，但不能保证每一帧动作都精确执行。
第三方实时会话可能按连接时长持续计费。停止回复只是停止当前输出，不一定结束计费。我们增加十秒空闲回收，在没有识别、生成和播放工作时，发送挂断并关闭控制连接。但本地麦克风继续监听。下次有人声，前端走保留输入的重连路径，不清掉触发重连的那句话。对话可以继续生成，发送台词前等待新连接就绪。连续讲话会刷新活动时间，正在回复也不算空闲。这个能力的难点是生命周期和首句保留，不是把一个常量从九十改成十。
最初全局只有一条管线时，第二个人可能一直连接中，停止操作也可能影响别人。修改后，每个页面有独立的 Pipeline、对话历史、VAD、取消句柄和数字人连接。重型语音权重仍共享，私人状态不共享。REST 请求用当前连接 token 找到所属会话，浏览器身份对应自己的照片和人设目录。云端部署默认最多八页对话、三路数字人，上限要在调用供应商创建接口之前检查。容量控制、请求归属和完整账号登录是不同层次，部署时不能把其中一个当成另一个。
Mac mini 的十六 GB 是统一内存，不等于十五 GiB 独立显存。Q 四 K M 权重约五点六三 GB，但真正运行还要容纳缓存、语音模型、系统和其他进程。我们采用分阶段释放：先清理人物运行时，让本地大脑生成文字，然后停止 llama server，再生成声音与口型。每段 MuseTalk 完成后也释放运行时。当前预算估算约十三点一 GiB，包含二点五 GiB 运行余量，但不是实测保证。重复加载会增加等待时间，所以需要在目标 Mac 同时记录延迟和内存压力。
桌面版需要管理后端进程，而不只是把网页套进窗口。Windows 用 Electron 启动 Python 服务，等待健康检查，处理启动错误，并在窗口退出时结束所属后端。后来还处理了新设置的用户环境变量无法被旧进程读取的问题。Mac 当前提供原生启动脚本和系统浏览器入口，尚不是签名分发的独立应用包。启动脚本限制为一个会话，设置本地模型配置和离线加载。正常按 Control 加 C 或关闭启动终端，应该结束服务，避免后台实例持续占用资源。
部署到 Linux 时，应用容器和 Nginx 容器分工明确。Invalid host header 属于 Host 校验问题，而麦克风是否可用属于浏览器安全上下文，两者不能混为一谈。允许外部 IP，不会自动让普通 HTTP 获得麦克风权限。公网需要可信的 HTTPS，Nginx 正确转发 WebSocket，后端的公开 origin 也要匹配 HTTPS。没有域名时可以按当前服务商条件申请 IP 证书，并设置自动续期。服务器部署还意味着麦克风数据会从浏览器传到你的后端；没有发给模型供应商，不等于没有离开用户电脑。
测试从小到大推进。先验证重采样、预算和解析，再模拟云端连接与回收，再检查浏览器控件和播放，最后做真实推理和用户确认。源码发布准备时，一百一十项后端检查通过，并完成前端回归。这个结果不代表目标 Mac 已经全部通过，也不代表每次运行都保证相同速度。实际调用付费服务的检查应单独执行，反复回归优先使用模拟协议。遇到没有输入文字的故障，就从麦克风和 PCM 起点排查；遇到字幕抢跑，就检查实际播放时钟。让证据沿着管线逐层收敛。
最后交付源码，而不是把开发机器整个打包。Git 忽略密钥、个人照片、人设、日志、运行时和模型文件。shell 与 command 文件固定使用 LF，并记录执行权限，避免 Windows 提交以后 Mac 不能启动。我们另外做了干净克隆，证明没有缓存模型和私人配置时，源码测试仍能通过；首次安装会自己准备缺少的权重。仓库名称最终改为 cyber girl，角色名仍是小满。你现在可以先验证文字，再打开语音，最后启用口型，分别记录首字、首音和视频生成的耗时。
回到最初这句话：今天有点累，陪我聊聊。好的交付，不是给它堆上最多的模型，而是让录音、理解、回应、声音和画面在真实使用中配合起来。你可以先关闭数字人完成语音闭环，再研究本地模型的内存和加载策略；也可以从人设、播放同步或者多人隔离继续扩展。完整的命令、代码路径、故障复盘和验证边界都在配套文字教程。接下来，把项目拉到你的 Mac 上，用自己的麦克风，完成属于你的那一次真实回复。
